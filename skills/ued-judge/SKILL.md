# UED 评价师（UEDJudge）

对**已开发完成**的 Web 系统、网页做体验诊断，并按用户选择执行分阶段优化。

整体版本以本文件的 `metadata.version` 为准，采用 `x.y.z`（大版本 / 优化迭代 / 问题修复）；与下方冻结评分正文的版本独立。

## 🚦 三条铁律

1. **先诊断，停下，再优化。** 诊断报告输出后必须结束本轮回复，等用户在「只要报告 / 逐阶段执行 / 一次性执行」中明确选择。用户选择前不得修改任何文件。
2. **评论员必须隔离。** 每次唤起都是全新上下文，只给截图和使用途径，逐字使用 [critic-prompt.md](references/critic-prompt.md) 的冻结正文（A 绝对评分 / B 成对比较）。成对比较时两个版本随机分配为 A/B，不告知新旧。不给代码、改动说明、历史评语、硬性检查结果，**也绝不提及任何评分阈值或目标**。主控不改写评论员的判定。
3. **成本有上限。** 子智能体调用：只要报告 2 次，一次性执行 5 次，逐阶段执行最多 7 次（评论员 + 核验员，主控自检不计）。同一流程内不新增阶段、不重新诊断；要继续优化只能由用户另起新流程。

> **用对比和验收判断改没改好，不靠两次绝对分相减。** 初评双样本取平均并区分高/低置信差距；复评用成对比较，依据指向本轮改动才算真实变化；收尾由核验员逐条核对初评差距。绝对分只在初评与收尾各出现一次，仅作参考。

## 流程速览

```
Step 0 识别输入（URL / 本地 HTML / 工程 / 仅截图）→ 判断能否执行优化
Step 1 写使用途径（界面类型 / 用户 / 场景 / 核心任务 / 关键路径），只写一次，全程复用
Step 2 截图：scripts/capture.mjs → 整页总览 + 1440×900 视口切片，参数全程一致
Step 3 初评：两个全新评论员（正文 A）→ 维度分取平均；合并差距为 G1…Gn，标高/低置信
Step 4 主控独立跑硬性检查：H 合规 / G 布局几何 / A 反模式 / L 认知负荷（+ W/M 补充）
Step 5 归纳为 1–3 个阶段，每条写可观察的目标状态；列保护清单、保真清单、可改善上限
Step 6 对话中输出诊断报告 → 给出三个选项 → 停下        ← 闸门
Step 5.5 用户选择执行后：写目标设计稿（./.ued-judge/targets/）
Step 7 按执行约束改 → 主控截图自检（≤2 轮）→ 成对复评（正文 B，随机 A/B）→ 维度判定
Step 8 收尾：核验员逐条核对 G1…Gn + 成对比较 + 一次绝对评分 → 按务实目标判定
```

完整规则见 [critic-protocol.md](references/critic-protocol.md)，以它为准。

## 输出约定

- 报告**只在对话中呈现**，用户要求保存时再写文件。
- 截图、目标稿与备份放在用户工作目录的 `./.ued-judge/`，流程结束时询问是否删除。
- 仅有截图输入时只出报告，不执行优化。
- 执行优化前确认可回退（Git 工作区干净或已备份）。
- **执行只读两样**：[execution-constraints.md](references/execution-constraints.md)（X1–X15）+ 本轮目标稿；视觉/动效/Web 方法按受影响区域查阅执行参考。约束是为了防止改错，不是限制力度：结构问题要做结构性修改。
- **功能与文案意图保真**：最大程度保留原页面功能、描述与业务信息；功能删减或语义变化须单独取得用户明确授权（X5、X6、X8）。
- **数据与界面分开评价**：业务数据本身及归因不明的问题只提示、不计分、不进优化阶段；界面文案与数据呈现缺陷仍评价。
- **评分口径**：现行冻结 prompt v3.1，与 v3、v2.x 分数不直接比较。修改冻结正文前须先做校准集验证（见 CONTRIBUTING）。
