# UED 评价师（UEDJudge）

对**已开发完成**的 Web 系统、网页做体验诊断，并按用户选择执行分阶段优化。

## 🚦 三条铁律

1. **先诊断，停下，再优化。** 诊断报告输出后必须结束本轮回复，等用户在「只要报告 / 逐阶段执行 / 一次性执行」中明确选择。用户选择前不得修改任何文件。
2. **评论员必须隔离。** 每次唤起都是全新上下文，只给截图和使用途径，逐字使用 [critic-prompt.md](references/critic-prompt.md) 的冻结正文。不给代码、实现细节、历史版本、历史评语、改动说明、硬性检查结果，**也绝不提及任何评分阈值**。主控不改写评论员的评分。
3. **成本有上限。** 评论员调用：只要报告 1 次，一次性执行 3 次，逐阶段执行最多 5 次（均含收尾双样本）。同一流程内不新增阶段、不重新诊断；要继续优化只能由用户另起新流程。

> **单次盲评有方差，按维度判定。** 同一截图多次盲评，单个维度通常只差 1 分，但合计会累加波动。复评时逐维度比较：某维度变化 ≥2 分，且该维度的差距指向本轮改动，才算真实变化；总分只作参考。收尾定分用两次独立盲评的平均，达线判断用较低分。

## 流程速览

```
Step 0 识别输入（URL / 本地 HTML / 工程 / 仅截图）→ 判断能否执行优化
Step 1 写使用途径（界面类型 / 用户 / 场景 / 核心任务 / 关键路径），只写一次，全程复用
Step 2 截图（1440×900 整页，参数全程一致，文件名中性）
Step 3 唤起全新评论员 → 审美方向 + 顶尖设想 + ≤5 条差距[维度·P] + 做得好的地方 + 6 维度评分
Step 4 主控独立跑硬性检查：H 合规 / A 反模式 / L 认知负荷
Step 5 归纳为 1–3 个阶段（P0/P1 与阻断项进阶段一；结构层先于表层）+ 保护清单
Step 6 对话中输出诊断报告 → 给出三个选项 → 停下        ← 闸门
Step 7 执行：复述预期方向、对照保护清单、记录改动清单；逐阶段（复评 + 维度判定）或一次性
Step 8 收尾双样本定分 → 收尾报告；较低换算分 ≥9 视为达到顶尖参考线
```

完整规则见 [critic-protocol.md](references/critic-protocol.md)，以它为准。

## 输出约定

- 报告**只在对话中呈现**，用户要求保存时再写文件。
- 截图与备份放在用户工作目录的 `./.ued-judge/`，流程结束时询问是否删除。
- 仅有截图输入时只出报告，不执行优化。
- 执行优化前确认可回退（Git 工作区干净或已备份）。
