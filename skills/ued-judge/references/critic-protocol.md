# 评审协议（critic-protocol）

UEDJudge 的完整工作流：**诊断 → 归纳分阶段 → 人工确认 → （可选）执行 → 复评 → 收尾**。本文件是流程、角色、隔离规则与成本边界的唯一事实源。

## 1. 角色

| 角色 | 承担者 | 职责 | 上下文 |
|---|---|---|---|
| 主控 | 当前会话的主 agent | 截图、写使用途径、唤起评论员、跑硬性检查、归纳分阶段、出报告、执行修改、复评调度 | 连续，掌握全部信息 |
| 评论员 | 每次全新创建的子智能体 | 按冻结 prompt 盲评一张截图 | **每次从零开始**，只知道截图 + 使用途径 |

不设第三个角色；修改由主控直接完成。

## 2. 流程

### Step 0 · 识别输入与能力边界

| 输入 | 可做 |
|---|---|
| URL / 本地 HTML / 可运行工程 | 诊断 + 硬性检查（完整）+ 可执行优化（需有源码写权限） |
| 仅截图 | 诊断 + 硬性检查（仅限肉眼可判项，其余标「无法判定」）；**不能执行优化**，只出报告 |
| 设计稿（Figma 等） | 导出截图后按「仅截图」处理 |

执行优化前确认目标可回退：Git 工作区干净，或先把将要修改的文件备份到 `./.ued-judge/backup/`。

### Step 1 · 写使用途径（只写一次）

中性、功能性描述，**不含任何审美评价、不暗示已知问题、不提改动历史**。固定四项：

```
用户：<谁在用，角色与熟练度>
场景：<在什么情境、多高频率下使用>
核心任务：<来这里要完成什么>
关键路径：<完成任务依次经过的界面区域与操作>
```

信息来源：用户说明 > 页面内容推断。推断不出的项请用户补充（一次性打包问，不超过 1 轮）。写定后**所有轮次原样复用**。

### Step 2 · 截图

- 固定参数，所有轮次一致：视口 `1440×900`、整页截图、同一浏览器。
- 推荐命令（需 Playwright，首次需 `npx playwright install chromium`，属于安装依赖，先告知用户）：

  ```bash
  npx playwright screenshot --full-page --viewport-size=1440,900 "<url 或 file:///绝对路径>" ./.ued-judge/shots/shot-<n>.png
  ```

- 没有截图能力时，请用户按同样视口手动截图并提供路径。
- 文件名保持中性（`shot-1.png`、`shot-2.png`），不带「优化后」「阶段一」等字样。

### Step 3 · 唤起评论员

- 使用 [critic-prompt.md](critic-prompt.md) 的**冻结正文**，只替换 `{screenshot_path}` 与 `{usage_pathway}`。
- 必须是**全新上下文**：Kiro 中用 `invoke_sub_agent`（`general-task-execution`），`prompt` 即替换后的正文，不传 `contextFiles`；其他工具用「不继承当前会话历史的独立调用」等价实现。
- 禁止传递：代码、实现细节、历史截图、历史评语、改动说明、评分阈值、轮次信息。
- 评论员输出原样保留，用于报告转录；主控不得改写其评分。

### Step 4 · 硬性检查（主控独立完成）

按 [hard-checks.md](hard-checks.md) 逐项检查，给出「通过 / 不通过 / 无法判定」+ 证据（元素、数值、代码位置）。硬性检查**不影响评论员评分**，在报告中与评论员结论并列呈现。

### Step 5 · 归纳为 1–3 个阶段

主控把「评论员差距清单（≤5 条）+ 硬性检查不通过项」聚类成阶段，每条先按 [glossary.md](glossary.md) 打标签：

- **依赖优先**：结构性问题（构图、层级、色彩体系、字体体系）先于表层打磨（微交互、装饰、文案）。
- **收益密度**：严重度高且改动集中的捆成阶段一；避免「一条差距一个阶段」。
- **硬性检查中的阻断项**（如正文对比度不达标、关键操作键盘不可达）一律进阶段一。
- 阶段数由聚类结果决定，问题集中时可以只有 1 个阶段。优先级：阶段一 P0 必做 / 阶段二 P1 重要 / 阶段三 P2 可选。

### Step 6 · 输出报告，停下等用户选择（闸门）

按 [report-template.md](report-template.md)「诊断报告」**在对话中输出**（不写文件；用户要保存再保存）。结尾给出三个选项后**结束本轮回复**：

1. 只要报告，到此为止。
2. 逐阶段执行（每阶段后复评，动态调整后续阶段）。
3. 按顺序一次性执行全部阶段（最后统一复评一次）。

用户未明确选择前，不得修改任何文件。用户可以指定只执行部分阶段（如「只做阶段一」）。

### Step 7 · 执行

**逐阶段执行**
1. 执行当前阶段的改动（只做本阶段范围内的事）。
2. 重新截图（Step 2 同参数）→ 唤起**全新**评论员（同一冻结 prompt、同一使用途径）→ 重跑硬性检查。
3. 按 [report-template.md](report-template.md)「阶段复评简报」输出结果，并据复评结果**调整后续阶段**的具体动作（可合并、重排、替换，但不新增第 4 个阶段）。
4. 进入下一阶段前是否需要再停下确认：默认连续执行；用户要求「每阶段确认」时逐阶段停下。

**一次性执行**
1. 严格按诊断报告中的阶段顺序完成全部改动。
2. 结束后截图 → 全新评论员复评一次 → 重跑硬性检查。

**退化处理**：某次复评分数低于上一次时，在简报中如实写出，判断原因（改动方向错误 / 评论员主观波动），并给出建议：回退该阶段（用 Git 或 `.ued-judge/backup/`）或保留。回退属于修改文件，须用户确认。

### Step 8 · 收尾

按 [report-template.md](report-template.md)「收尾报告」输出：评分变化轨迹、各阶段完成情况、硬性检查前后对比、剩余差距。

- 评论员最终评分 ≥ 9：视为达到顶尖水准参考线。
- 最终评分 < 9：如实说明未达线及剩余差距，可建议用户**另起一轮新诊断**（从 Step 2 重新开始，需用户主动发起）。不得在本次流程内自行追加轮次。

结束时告知 `./.ued-judge/` 下有截图与备份，询问是否删除；用户不回应则保留。

## 3. 成本边界（硬上限）

| 用户选择 | 评论员调用次数 |
|---|---|
| 只要报告 | 1 |
| 一次性执行 | 2（诊断 1 + 最终复评 1） |
| 逐阶段执行 | ≤ 4（诊断 1 + 每阶段复评 1，最多 3 个阶段） |

动态调整只能改写既有阶段的内容，**不能新增阶段、不能在同一流程内重新诊断**。任何超出上限的继续优化都必须是用户主动发起的新流程。

## 4. 隔离规则（评分客观性的底线）

1. 评论员每次都是全新上下文。
2. 评论员只拿到截图 + 使用途径，别无他物。
3. 每次使用逐字相同的冻结 prompt。
4. 使用途径首轮写定后不改。
5. 截图参数每轮一致，文件名中性。
6. **9 分参考线只存在于本协议与主控判断中，绝不出现在评论员 prompt 或传给评论员的任何内容里。**
7. 主控不得对评论员的评分做「修正」或「解读性加减分」。
