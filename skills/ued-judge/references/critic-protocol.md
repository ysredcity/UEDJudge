# 评审协议（critic-protocol）

UEDJudge 的完整工作流：**诊断 → 归纳分阶段 → 人工确认 → （可选）执行 → 复评 → 收尾**。本文件是流程、角色、隔离规则与成本边界的唯一事实源。

## 1. 角色

| 角色 | 承担者 | 职责 | 上下文 |
|---|---|---|---|
| 主控 | 当前会话的主 agent | 截图、写使用途径、唤起评论员、跑硬性检查、归纳分阶段、出报告、执行修改、复评调度 | 连续，掌握全部信息 |
| 评论员 | 每次全新创建的子智能体 | 按冻结 prompt 盲评截图 | **每次从零开始**，只知道截图 + 使用途径 |

不设第三个角色；修改由主控直接完成。

## 2. 流程

### Step 0 · 识别输入与能力边界

| 输入 | 可做 |
|---|---|
| URL / 本地 HTML / 可运行工程 | 诊断 + 硬性检查（完整）+ 可执行优化（需有源码写权限） |
| 仅截图 | 诊断 + 硬性检查（仅限肉眼可判项，其余标「无法判定」）；**不能执行优化**，只出报告 |
| 设计稿（Figma 等） | 导出截图后按「仅截图」处理 |

执行优化前确认目标可回退：Git 工作区干净，或先把将要修改的文件备份到 `./.ued-judge/backup/`。

### Step 1 · 写使用途径（只写一次）

中性、功能性描述，**不含任何审美评价、不暗示已知问题、不提改动历史**。固定五项：

```
界面类型：<任务型工具 | 品牌展示>
用户：<谁在用，角色与熟练度>
场景：<在什么情境、多高频率下使用>
核心任务：<来这里要完成什么>
关键路径：<完成任务依次经过的界面区域与操作>
```

**界面类型**决定评论员用哪套口径判断"AI 生成感"，必须由主控判定并写明：
- **任务型工具**：设计为任务服务，用户在完成工作。后台、看板、数据表、设置页、内部工具、登录后的应用界面。
- **品牌展示**：设计本身就是要传达的内容。官网、落地页、营销活动页、作品集、长文内容页。
- 判定依据按优先级：用户说明 > 页面主要用途。一个页面兼有两种成分时（如带营销首屏的产品首页），按用户完成核心任务时所在的部分判定。这是事实分类，不是审美评价，不违反"使用途径保持中性"。

信息来源：用户说明 > 页面内容推断。推断不出的项请用户补充（一次性打包问，不超过 1 轮）。写定后**所有轮次原样复用**。

### Step 2 · 截图

- 固定参数，所有轮次一致：视口 `1440×900`、整页截图、同一浏览器。
- 推荐命令（需 Playwright，首次需 `npx playwright install chromium`，属于安装依赖，先告知用户）：

  ```bash
  npx playwright screenshot --full-page --viewport-size=1440,900 "<url 或 file:///绝对路径>" ./.ued-judge/shots/shot-<n>.png
  ```

- 没有截图能力时，请用户按同样视口手动截图并提供路径。
- 文件名保持中性（`shot-1.png`、`shot-2.png`），不带「优化后」「阶段一」等字样。

**主截图取默认态，评分锚定默认态**：截页面首次加载的默认呈现。评论员的评分应基于这个默认态，它才是用户每天实际看到的样子。

**何时补充状态截图（谨慎，不滥补）**：
- **折叠了核心评估内容**才补展开态。区分两种折叠：① 把**低频操作**（如配置/凭证表单）收起，是**有意的设计优化**，此时**不要**补展开态，否则评论员会把「展开后表单占满首屏」当成默认缺陷（实测观察：补了配置展开态后，评论员指出"低频表单占据首屏黄金位"）；② 折叠**隐藏了本该被评估的主内容**（如唯一的数据列表被默认收起），这才补展开态。
- **关键交互态**（loading、操作成功反馈、表格 hover、空/错误态）在设计的核心价值依赖它们时才补 1–3 张，用于消除"静态整页看不到已实现交互、导致漏判或误扣"的盲区。日常列表/表单类页面通常无需补。

**补充截图仅作参考、不改变默认态基准**：多张时给评论员一并、平等提供，命名一律中性（`shot-<n>-a.png`…），不得用文件名或附注暗示版本/交互态/第几张。评论员 prompt 的 `{screenshot_path}` 列出全部路径（每行一个），其余正文不变。**能用默认态说清楚的，就只给默认态一张。**

### Step 3 · 唤起评论员

- 使用 [critic-prompt.md](critic-prompt.md) 的**冻结正文**，只替换 `{screenshot_path}` 与 `{usage_pathway}`。
- 必须是**全新上下文**：Kiro 中用 `invoke_sub_agent`（`general-task-execution`），`prompt` 即替换后的正文，不传 `contextFiles`；其他工具用「不继承当前会话历史的独立调用」等价实现。
- 禁止传递：代码、实现细节、历史截图、历史评语、改动说明、评分阈值、轮次信息、硬性检查结果。
- 评论员输出五部分：审美方向、顶尖水准设想、差距清单（≤5 条，每条带 `[维度 · P0–P3]`）、做得好的地方（2–3 条）、6 维度 0–4 分及合计 `/24`。
- 主控按 [critic-prompt.md](critic-prompt.md)「评分输出与换算」换算 10 分制。评论员输出原样保留，主控不得改写其评分。

数据核对提示附在差距清单步骤中，与最多 5 条界面差距分列。评论员按冻结正文区分业务数据、界面文案与数据呈现；数据本身及归因不明的问题不计分。主控记录本流程的 prompt 版本，全程使用相同正文；升级口径须在用户发起的新流程中重新建立基线，不回填历史分数，不用跨版本分差判定优化效果。若评论员误将数据提示用于扣分，如实标记“评分依据越界，不能据此归因”，不得由主控事后加分或改写原样本；不为纠正这一点突破调用上限。

### Step 4 · 硬性检查（主控独立完成）

按 [hard-checks.md](hard-checks.md) 执行四组检查，给出「通过 / 不通过 / 无法判定」+ 证据（元素、数值、代码位置）：
- **H 组**：合规项（对比度、焦点、键盘、可访问名、状态覆盖等）。
- **G 组**：布局几何（同排按钮与输入框的控件本体对齐，不把标签高度计入对齐盒子）。
- **A 组**：可机检的反模式（单侧彩色边框、渐变文字、卡片嵌套等）。
- **L 组**：认知负荷计数（首屏核心指标数、决策点选项数等）。

硬性检查**不影响评论员评分**，结果不传给评论员，在报告中与评论员结论并列呈现。

数据本身的问题单列核对提示，不转换为 H9 状态覆盖失败或 L 组负荷失败。只有独立证据证明相关界面状态缺失、呈现不当或现有操作受阻，才按对应检查项记录；数据内容不豁免对比度、字号、布局与可访问性要求。

同时按 [web-interface-quality.md](web-interface-quality.md) 检查关键路径中适用的 W 组；含动效或拟改反馈/过渡时按 [motion-optimization.md](motion-optimization.md) 检查 M 组。W/M 是工程补充，不是额外审美评分或 WCAG 等级认证，不纳入 L 组计数；与 H/G 重叠的失败只记在原项，补充结果引用其编号。不存在相关行为时说明不适用，缺少实测能力时标无法判定。问题按实际影响归入既有阶段，不增加评论员调用。

### Step 5 · 归纳为 1–3 个阶段

主控把「评论员差距清单 + 硬性检查不通过项」聚类成阶段，每条先按 [glossary.md](glossary.md) 打标签：

- **严重度映射**：评论员标 P0、P1 的差距与硬性检查的「阻断」项进阶段一；P2 按收益归入阶段一或二；P3 进最后一个阶段或舍弃。
- **依赖优先**：结构性问题（构图、层级、色彩体系、字体体系）先于表层打磨（微交互、装饰、文案）。
- **收益密度**：严重度高且改动集中的捆成一个阶段，避免「一条差距一个阶段」。
- **保护清单**：评论员列出的「做得好的地方」整理为保护清单，写进报告。任何阶段的改动都不得削弱清单里的元素；确实需要改动时，在报告中写明原因。
- 阶段数由聚类结果决定，问题集中时可以只有 1 个阶段。

**数据提示不进 UI 优化阶段**：保留原始值与业务正文，核对提示在报告中单列，不当作 P0/P1 或必做项，不自动新增数据治理功能。若用户明确要求核对或修正业务数据，作为另行授权范围处理；同一区域独立可见的呈现问题仍可归入阶段。不得为冲高分删除数据、缩减业务含义或弱化评分锚点。

**建立功能与文案保真清单（主控）**：以优化前页面为基线，记录本次改动涉及的功能入口、操作结果、关键状态，以及原有描述的业务含义（操作对象、范围、条件、统计口径、单位、风险、限制与承诺）。检查相关非默认态和源码；无法验证的项注明「无法判定」，不根据截图猜测功能不存在。清单在对话报告中呈现，与评论员的视觉保护清单分别列出；未逐项列出的原有功能和描述仍默认保留。该清单不传给评论员。

视觉方案按 [visual-optimization.md](visual-optimization.md) 明确焦点、字体角色、颜色角色、表面层级与密度；沿用有效设计系统，不以行业默认色或装饰替代判断。涉及动效时记录触发、前后状态与收益，并纳入既有阶段，不能把“增加动效”当作无条件目标。方案仍只在对话呈现，遵守 Step 6 闸门。

### Step 6 · 输出报告，停下等用户选择（闸门）

按 [report-template.md](report-template.md)「诊断报告」**在对话中输出**（不写文件；用户要保存再保存）。结尾给出三个选项后**结束本轮回复**：

1. 只要报告，到此为止。
2. 逐阶段执行（每阶段后复评，动态调整后续阶段）。
3. 按顺序一次性执行全部阶段（最后统一复评）。

用户未明确选择前，不得修改任何文件。用户可以指定只执行部分阶段（如「只做阶段一」）。

### Step 7 · 执行

**动手前先复述预期效果方向**：对每条要处理的差距，先用一句话写下「改完后应该变得更 X」（如"区块间视觉差异应变大""红色使用面积应变小"），再对照 [glossary.md](glossary.md) 里该标签的修复方向说明（若有）确认没有理解反。诊断正确但修复方向理解反，是比"改过头"更隐蔽的失败模式（实测观察：把"卡片权重扁平"做成了去边框、改通栏分割线，复评评论员指出它"像未排版的原始数据导出"）。

**对照保护清单**：动手前核对改动范围是否触及保护清单中的元素。

**功能与文案意图保真（执行约束）**：
- UI 优化应最大程度保留原页面的功能、描述与业务信息，优先改布局、层级、样式与呈现方式。不能以降噪、缩短页面或提高评分为由删除功能、数据字段、说明、风险提示或操作反馈，也不能把真实功能替换成静态展示、示例数据或无实际行为的按钮。
- 移动入口、合并重复呈现或折叠低频内容时，原有能力和信息须仍可发现、可访问、可操作；保持关键状态、输入值与结果反馈，不让高频或关键任务因隐藏而受阻。
- 默认保留原文；仅在不影响文案意图表达时做纠错、精炼或澄清。修改前后须保持操作对象、范围、条件、统计口径、单位、风险、限制、语气强度与承诺一致。不能将「示例」改为「已同步」、「申请」改为「完成」，或为缩短文案删去适用条件。业务专名、数据、乱码或歧义无法可靠确认时，保留原内容并提示核对，不擅自补写或猜改。
- 确需删减功能、移除信息或改变语义时，先说明原内容、拟改内容及影响，并取得用户针对该变化的明确授权；「优化 UI」或同意执行阶段不等于授权功能删减或语义变化。等待选择期间可继续不依赖该选择的已授权改动，不擅自实施争议部分。

**保真核验（每轮修改后）**：对照优化前基线与保真清单，回归受影响的入口、关键路径、状态和操作结果，检查桌面与相关移动视口的可达性；逐条记录文案「原文 → 新文案 → 原意为何保持」。无文案改动时注明未改；无法验证的功能如实列出，不宣称全量保留已验证。发现非授权的功能遗漏或语义漂移，先修复，无法安全修复则报告并等待用户选择，不把它作为优化完成。该核验独立于盲评分数，分数提高不能抵消功能或语义损失。

**验证控件对齐**：修改工具栏、筛选或表单布局后，按 G1 在相关视口比较控件本体的对齐线；标签、提示与按钮文案变化不能造成意外错位。截图盲评未指出此问题，也须由主控独立检查。

**色彩优化先确认作用**：区分品牌/主操作色、语义色与装饰色，先说明每种颜色服务的任务与层级。诊断没有指出主色本身存在问题时，保留其识别作用；需要降噪时优先调整使用面积、饱和度、位置与重复次数，不默认去色或改成黑白灰。色彩变丰富也必须对应具体收益（如主操作更易找到、表面层次更清楚），不为避免单调而添加无关颜色。

**按执行参考落地与回归**：涉及视觉改动时对照局部设计契约；涉及交互时核查 W 组受影响项；涉及动效时核查 M 组正常、连续操作、失败恢复与减弱动效。记录实测或短录屏证据及无法判定项，不仅查看 CSS 是否有 transition。静态截图不证明时序、缓动或流畅性；动效证据只供主控，不改变 Step 2/3 评论员输入。无动效也可是正确选择；不得为验证新增产品功能或另开优化阶段。

**记录本轮改动清单**：每轮动手时同步记下改了哪些元素（选择器 / 区块 / 文案），供复评后做差异归因。没有这份清单就无法区分真实变化与评分噪声。

**逐阶段执行**
1. 执行当前阶段的改动（只做本阶段范围内的事）。
2. 重新截图（Step 2 同参数）→ 唤起**全新**评论员（同一冻结 prompt、同一使用途径）→ 重跑硬性检查。
3. 按 [report-template.md](report-template.md)「阶段复评简报」输出结果，并据复评结果**调整后续阶段**的具体动作（可合并、重排、替换，但不新增第 4 个阶段）。
4. 进入下一阶段前是否需要再停下确认：默认连续执行；用户要求「每阶段确认」时逐阶段停下。

**一次性执行**
1. 严格按诊断报告中的阶段顺序完成全部改动。
2. 结束后截图 → 按 Step 8「收尾定分用双样本」复评两次 → 重跑硬性检查。

逐阶段执行时，最后一个阶段的复评即为收尾第一个样本，再补一次即可。

**每轮只针对当前最大差距、避免改过头**：一次改动只解决排序最高的问题，力度足够但不过度。为了强调某元素而把它做成全场压倒性焦点，往往会引入新问题（实测观察：把次要指标放大成超大英雄数字后，复评评论员指出它与另一个大数字"焦点分裂"）。改动要克制、可回溯，不要一轮内叠加多个大改。

**分数变化判定（以维度分为准）**：评论员单次盲评有方差。对照实验中，同一截图用同一 prompt 评 3 次，每个维度的分数极差都 ≤1，但 6 个维度的 ±1 会同向累加，合计极差达到 4/24（约 1.7 分）。因此判定改动效果时**看维度分，不看总分**：

1. **维度变化判定**：逐维度对比本次与上次的分数。
   - 某维度变化 **≥2 分**：候选的真实变化。
   - 某维度变化 **1 分**：视为噪声。
2. **差异归因核查**：对候选的真实变化，查看该维度下的差距条目，对照「本轮改动清单」，标注指向本轮改动的元素还是未改动的元素。
   - 该维度的差距指向本轮改动 → 判为**真实变化**（下降即真退步，上升即真改进）。
   - 该维度的差距都指向未改动的元素 → 视为噪声。
3. **总分只作参考**：换算后的 10 分制总分照实记录，但不单独作为保留或回退的依据。

判为**真退步** → 优先回退该维度相关的改动（Git 或 `.ued-judge/backup/`），换一种根本解法，而不是在已被否定的做法上继续微调。判为噪声 → 保留当前版本，在简报中写明判定过程。回退属于修改文件，须用户确认。

上述阈值来自一次对照实验（n=3，见 `PROJECT_CONTEXT.md`），属于初始值；案例积累后记录校准依据再调整。

### Step 8 · 收尾

**收尾定分用双样本**：最终复评是拍板节点，对最终版本的同一张截图再唤起**一次全新**评论员（同一冻结 prompt、同一使用途径、同一截图），得到两个独立样本：
- 报告中写出两个样本的维度分与合计；**定论 = 两次合计的平均**，换算 10 分制；各维度也写出平均分。
- 判断是否达到 9 分参考线时，用**两个样本中较低的换算分**（保守）。
- 同一维度两次相差 ≥2 分时，在报告中注明该维度「评分不稳定」；剩余差距优先采信两次都出现的条目。

平时轮次（诊断、逐阶段复评）仍为单样本，只有收尾这一个节点加一次。

按 [report-template.md](report-template.md)「收尾报告」输出：评分变化轨迹、各阶段完成情况、硬性检查前后对比、保护清单是否完好、剩余差距。

- 较低换算分 ≥ 9：视为达到顶尖水准参考线。
- 较低换算分 < 9：如实说明未达线及剩余差距，可建议用户**另起一轮新诊断**（从 Step 2 重新开始，需用户主动发起）。不得在本次流程内自行追加轮次。

结束时告知 `./.ued-judge/` 下有截图与备份，询问是否删除；用户不回应则保留。

## 3. 成本边界（硬上限）

| 用户选择 | 评论员调用次数 |
|---|---|
| 只要报告 | 1 |
| 一次性执行 | 3（诊断 1 + 收尾双样本 2） |
| 逐阶段执行 | ≤ 5（诊断 1 + 每阶段复评 1，最多 3 个阶段 + 收尾加样 1） |

动态调整只能改写既有阶段的内容，**不能新增阶段、不能在同一流程内重新诊断**。任何超出上限的继续优化都必须是用户主动发起的新流程。

## 4. 隔离规则（评分客观性的底线）

1. 评论员每次都是全新上下文。
2. 评论员只拿到截图 + 使用途径，别无他物。
3. 每次使用逐字相同的冻结 prompt。
4. 使用途径（含界面类型）首轮写定后不改。
5. 截图参数每轮一致，文件名中性。
6. **9 分参考线只存在于本协议与主控判断中，绝不出现在评论员 prompt 或传给评论员的任何内容里。** 冻结 prompt 中的分档描述对每一档一视同仁，不得单独强调某一档。
7. 主控不得对评论员的评分做「修正」或「解读性加减分」。分数变化判定与双样本平均只影响**决策**（保留 / 回退 / 是否达线），每个样本的原始分数都照实记录。
8. 硬性检查结果与主控使用的任何检测工具输出，都不传给评论员。
