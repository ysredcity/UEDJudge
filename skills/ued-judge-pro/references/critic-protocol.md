# 评审协议（critic-protocol）

UEDJudge 的完整工作流：**诊断 → 归纳分阶段 → 人工确认 → （可选）目标稿 → 执行与自检 → 成对复评 → 收尾核验**。本文件是流程、角色、隔离规则与成本边界的唯一事实源。

## 1. 角色

| 角色 | 承担者 | 职责 | 上下文 |
|---|---|---|---|
| 主控 | 当前会话的主 agent | 截图、写使用途径、唤起评论员与核验员、跑硬性检查、归纳阶段、写目标稿、执行修改与自检、出报告 | 连续，掌握全部信息 |
| 评论员 | 每次全新创建的子智能体 | 按冻结 prompt 盲评：正文 A 绝对评分，或正文 B 成对比较 | **每次从零开始**，只知道截图 + 使用途径 |
| 核验员 | 收尾时全新创建的子智能体 | 按 [verifier-prompt.md](verifier-prompt.md) 逐条核对初评差距是否解决，不打分 | 全新上下文，只知道改前/改后截图 + 使用途径 + 原始差距清单 |

评分（评论员）与验收（核验员）分开：评论员保持完全盲评；核验员知道改前改后，但不评价优劣、不给分。修改由主控直接完成。

## 2. 流程

### Step 0 · 识别输入与能力边界

| 输入 | 可做 |
|---|---|
| URL / 本地 HTML / 可运行工程 | 诊断 + 硬性检查（完整）+ 可执行优化（需有源码写权限） |
| 仅截图 | 诊断 + 硬性检查（仅限肉眼可判项，其余标「无法判定」）；**不能执行优化**，只出报告 |
| 设计稿（Figma 等） | 导出截图后按「仅截图」处理 |

执行优化前确认目标可回退：Git 工作区干净，或先把将要修改的文件备份到 `./.ued-judge/backup/`。

### Step 1 · 写使用途径（只写一次）

中性、功能性描述，**不含任何审美评价、不暗示已知问题、不提改动历史**。固定五项：

```
界面类型：<任务型工具 | 品牌展示>
用户：<谁在用，角色与熟练度>
场景：<在什么情境、多高频率下使用>
核心任务：<来这里要完成什么>
关键路径：<完成任务依次经过的界面区域与操作>
```

**界面类型**决定评论员用哪套口径判断 E4 与"AI 生成感"，必须由主控判定并写明：
- **任务型工具**：设计为任务服务，用户在完成工作。后台、看板、数据表、设置页、内部工具、登录后的应用界面。
- **品牌展示**：设计本身就是要传达的内容。官网、落地页、营销活动页、作品集、长文内容页。
- 判定依据按优先级：用户说明 > 页面主要用途。兼有两种成分时，按用户完成核心任务时所在的部分判定。这是事实分类，不违反"使用途径保持中性"。

信息来源：用户说明 > 页面内容推断。推断不出的项请用户补充（一次性打包问，不超过 1 轮）。写定后**所有轮次原样复用**。

### Step 2 · 截图（总览 + 视口切片）

**为什么切片**：多模态模型读图时会把长边压到约 1500px 量级。1440×2000 的整页图被压缩后，12–14px 文字和表格数字会进一步缩小，D、E 类细节判断时好时坏。整页总览保留构图信息，视口切片保证细节可读。

- 用 skill 自带脚本，参数固定、所有轮次一致：

  ```bash
  node <skill 目录>/scripts/capture.mjs "<url 或 file:///绝对路径>" ./.ued-judge/shots shot-<n>
  ```

  输出 `shot-<n>-0.png`（整页总览）与 `shot-<n>-1.png…`（1440×900 切片，相邻重叠 100px，最多 6 张），并打印 JSON 清单。视口 1440×900、像素密度 1、Chromium，不要改。
- 需要 Playwright。首次需 `npx playwright install chromium`，属于安装依赖，先告知用户；本机未全局安装时用环境变量 `PLAYWRIGHT_PATH` 指向 playwright 包。
- 没有截图能力时，请用户按 1440×900 视口提供首屏截图与向下滚动的若干张截图，按同样规则命名。
- 页面超过 6 张切片时（JSON 中 `truncated: true`），在报告中注明评论员未看到的区域。
- 文件名保持中性，不带「优化后」「阶段一」等字样。

**评分锚定默认态**：截页面首次加载的默认呈现。

**何时补充状态截图（谨慎，不滥补）**：
- 折叠**隐藏了本该被评估的主内容**（如唯一的数据列表被默认收起）才补展开态；低频操作（配置、凭证表单）收起是有意的设计，**不要**补展开态。
- 核心价值依赖交互态（loading、操作成功反馈、空/错误态）时才补 1–3 张，命名 `shot-<n>-a.png`…，追加在清单末尾。能用默认态说清楚的，只给默认态。

### Step 3 · 初评：评论员双样本

- **调用两个**全新评论员（可并行），都使用 [critic-prompt.md](critic-prompt.md)「正文 A」，只替换 `{screenshot_path}` 与 `{usage_pathway}`，两次输入完全相同。
- 全新上下文：Kiro 中用 `invoke_sub_agent`（`general-task-execution`），`prompt` 即替换后的正文，不传 `contextFiles`；其他工具用「不继承当前会话历史的独立调用」等价实现。
- **固定评委模型**：平台允许选择模型时，本流程内所有评论员与核验员用同一模型；不能选择时，在报告中记录实际使用的子智能体类型/模型。模型变化后的分数不与之前比较。
- 禁止传递：代码、实现细节、历史截图、历史评语、改动说明、评分阈值、轮次信息、硬性检查结果。
- 主控按 [critic-prompt.md](critic-prompt.md)「评分输出与换算」核对计数并换算。评论员输出原样保留，主控不改写判定。

**合并双样本**：
- **维度分 = 两样本平均**（可为 .5），合计取平均后换算 10 分制。同一维度两样本相差 ≥2 时标注「评分不稳定」。
- **勾选项**：两样本都判「不满足」的项为**高置信缺口**；只有一个样本判不满足的为低置信缺口。
- **差距清单**：按主题合并两份差距清单，两样本都提到的主题为**高置信差距**，只出现一次的为**低置信差距**。合并后每条保留评论员原话（取表述更具体的一条），编号 G1…Gn，这份清单即收尾核验的 `{gap_list}`。差距标注 `[项号 · 严重度]`，项号首字母即维度；两样本对同一主题给的项号不同时，两个都保留。
- **差距与勾选一致性**：P0–P2 差距对应的勾选项被判「满足」时，标记「差距与勾选不一致」，原分照记、不改判，该差距照常进入合并清单与阶段归纳。
- **保护清单**：两样本「做得好的地方」合并去重。
- **数据核对提示**：合并去重，单列。

**格式不完整**：样本缺少 24 行逐项判定表、只给维度汇总时，标记「格式不完整」，维度分照实记录，但该样本的勾选项不参与高置信缺口判定；不为补齐格式额外调用（校准实验中出现过一次子智能体只回摘要的情况）。

若评论员误将数据问题作为「不满足」依据，如实标记「依据越界」，该项按原判定计数，不由主控改判；不为纠正这一点突破调用上限。

### Step 4 · 硬性检查（主控独立完成）

按 [hard-checks.md](hard-checks.md) 执行四组检查，给出「通过 / 不通过 / 无法判定」+ 证据（元素、数值、代码位置）：
- **H 组**：合规项（对比度、焦点、键盘、可访问名、状态覆盖等）。
- **G 组**：布局几何（同排控件本体对齐）。
- **A 组**：可机检的反模式。
- **L 组**：认知负荷计数。

硬性检查**不影响评论员评分**，结果不传给评论员，在报告中并列呈现。数据本身的问题单列核对提示，不转换为 H9 或 L 组失败；数据内容不豁免对比度、字号、布局与可访问性要求。

同时按 [web-interface-quality.md](web-interface-quality.md) 检查关键路径中适用的 W 组；含动效或拟改反馈/过渡时按 [motion-optimization.md](motion-optimization.md) 检查 M 组。W/M 是工程补充，不纳入 L 组计数；与 H/G 重叠只记原项。不适用说明原因，缺少实测能力标无法判定。

### Step 5 · 归纳为 1–3 个阶段

主控把「合并差距清单 + 高置信勾选缺口 + 硬性检查不通过项」聚类成阶段，每条先按 [glossary.md](glossary.md) 打标签：

- **严重度映射**：P0、P1 差距与硬性检查「阻断」项进阶段一；P2 按收益归入阶段一或二；P3 进最后一个阶段或舍弃。
- **置信度优先**：同等严重度下，高置信差距与高置信缺口先于低置信项。低置信 P3 默认舍弃。
- **依赖优先**：结构层（构图、层级、内容组织）先于系统层（字体、色彩、间距），系统层先于表层（交互反馈、文案、装饰）。
- **收益密度**：严重度高且改动集中的捆成一个阶段，避免「一条差距一个阶段」。
- **保护清单**：合并后的「做得好的地方」写进报告，任何阶段不得削弱（X4）。
- 阶段数由聚类结果决定，可以只有 1 个。

**每条改动写「目标状态」**：在阶段表中，每条差距都写一句可观察的目标状态，并尽量对应到勾选项，例如「A1 满足：首屏只剩风险摘要一个主焦点」「D3 满足：数字列右对齐、等宽」。这是 Step 5.5 目标稿和自检的依据。

**可改善上限**：把所有问题分成三类写进报告——① UI 可解决（进阶段）；② 依赖数据核对（只提示，不进阶段）；③ 需要功能或语义变更授权（列出，等用户单独授权）。让用户提前知道本轮优化能改善的范围。

**数据提示不进 UI 优化阶段**：保留原始值与业务正文，不当作 P0/P1 或必做项，不自动新增数据治理功能。用户明确要求核对或修正业务数据时，作为另行授权范围处理。

**建立功能与文案保真清单（主控）**：以优化前页面为基线，记录本次改动涉及的功能入口、操作结果、关键状态，以及原有描述的业务含义（操作对象、范围、条件、统计口径、单位、风险、限制与承诺）。检查相关非默认态和源码；无法验证的项注明「无法判定」。清单在报告中呈现，与视觉保护清单分列；未逐项列出的原有功能和描述仍默认保留。不传给评论员。

### Step 6 · 输出报告，停下等用户选择（闸门）

按 [report-template.md](report-template.md)「诊断报告」**在对话中输出**（不写文件；用户要保存再保存）。结尾给出三个选项后**结束本轮回复**：

1. 只要报告，到此为止。
2. 逐阶段执行（每阶段后成对复评，动态调整后续阶段）。
3. 按顺序一次性执行全部阶段（最后统一复评）。

用户未明确选择前，不得修改任何文件。用户可以指定只执行部分阶段（如「只做阶段一」）。

### Step 5.5 · 目标设计稿（用户选择执行后、动手前）

用户选择执行后，不再新增闸门，主控先为每个要执行的阶段写目标稿，存到 `./.ued-judge/targets/stage-<n>.md`（结构层改动可附 SVG / HTML 线框）：

```
区域：<受影响的区块>
差距 → 目标状态：G2 → A1 满足：首屏只剩风险摘要一个主焦点 …
改完应更 X：<区块间差异应变大 / 红色面积应变小 …>（对照 glossary 修复方向）
布局草图：<结构层改动必填：线框或文字描述的区块排列、相对尺寸>
视觉契约：焦点 / 字体角色 / 色彩角色 / 表面层级 / 密度（只写受影响的）
保护与保真：涉及的保护清单项、保真清单项
```

目标稿是执行的唯一依据，执行时只读 [execution-constraints.md](execution-constraints.md) + 目标稿，具体方法按需查执行参考。

### Step 7 · 执行、自检与复评

**执行**：按目标稿修改，遵守 [execution-constraints.md](execution-constraints.md)（X1–X15）。同步记录改动清单（X13）。

**主控自检循环（每阶段完成后，不消耗评论员调用）**：
1. 用 Step 2 同参数重新截图，主控**亲自查看**总览与切片。
2. 逐条对照目标稿：每条「目标状态」是否在截图中可见地达成；目标对应的勾选项按正文 A 的判定规则自判是否已满足。
3. 检查是否引入新问题：新的焦点竞争、错位、信息或操作找不到、保护清单项变弱。
4. 跑保真核验（X5/X6）与受影响的 H/G/W/M 回归。
5. 有未达成或新问题 → 修正后回到 1。**自检最多 2 轮**，仍未达成的在简报中如实写明，不无限打磨。

自检是主控的执行质量控制，**不产生分数，不传给评论员或核验员**。

**成对复评（评论员正文 B）**：
- 对比对象：逐阶段执行时为「上一个保留版本 vs 本阶段版本」；一次性执行时为「初始版本 vs 最终版本」。
- **随机分配 A/B**：用 `node -e "console.log(Math.random()<0.5?'新=A':'新=B')"` 决定，主控记录分配表，不告诉评论员。两套截图都用 Step 2 的同参数截图，初始版本复用初评截图。
- **文件名与方案标签一致**：按分配表把两套截图复制为 `./.ued-judge/pair-<n>/pair-a-<i>.png` 与 `pair-b-<i>.png`（`<i>` 与原切片序号一致），`{set_a_paths}` 只列 `pair-a-*`，`{set_b_paths}` 只列 `pair-b-*`。v3.1 校准中，文件名不随标签变化时，评论员两次都按图像内容认定 A/B，有一次与分配表对调；文件名改为 pair-a / pair-b 后识别正确（n=1）。
- 主控按分配表把结果还原为「新版更好 / 持平 / 旧版更好」。
- **还原前先核对标签**：用评论员第 0 步「方案识别」（必要时结合第 1 步「可见差异」）核对 A/B 是否与分配表一致（例如它说「方案 A：顶部是一行折叠的配置条」，而折叠的是新版，则 A 应为新版）。描述与分配表相反时，标记「标签错位」，按描述内容还原；描述无法判断归属时，该次结果标记无效，只作参考，不为此追加调用。（v3 试跑中出现过一次评论员把 A/B 对调描述的情况。）

**维度判定规则**：

| 成对比较结果 | 依据是否指向本轮改动清单 | 判定 |
|---|---|---|
| 新版更好，把握高 | 是 | **真实改进** |
| 新版更好，把握低 | 是 | 倾向改进（不作为保留/回退依据） |
| 旧版更好（把握高或低） | 是 | **真退步**（建议回退该维度相关改动） |
| 任一方更好 | 否（指向未改动元素） | 噪声 |
| 持平 | — | 持平 |

判为真退步 → 优先回退相关改动（Git 或 `./.ued-judge/backup/`），换根本解法，而不是在被否定的做法上继续微调（X15）。回退须用户确认。正文 B 第 3 步列出的「新版独有问题」若指向本轮改动，记入后续阶段调整或剩余差距。

**逐阶段执行**
1. 执行当前阶段 → 自检循环 → 成对复评 → 重跑受影响的硬性检查。
2. 按 [report-template.md](report-template.md)「阶段复评简报」输出，并据结果**调整后续阶段**的具体动作（可合并、重排、替换，不新增第 4 个阶段）。
3. 默认连续执行；用户要求「每阶段确认」时逐阶段停下。

**一次性执行**
1. 按阶段顺序完成全部改动，每个阶段完成后都跑自检循环。
2. 全部完成后进入 Step 8，由收尾成对比较「初始 vs 最终」承担复评。

### Step 8 · 收尾

收尾三项证据，按重要性排序：

1. **差距核验（核验员，1 次）**：唤起全新核验员，使用 [verifier-prompt.md](verifier-prompt.md)，传入初评截图、最终截图、使用途径与合并差距清单 G1…Gn。若某条差距所在区域在最终版本中被**默认折叠**，在 `{after_paths}` 末尾追加该区域的展开态截图（`shot-<n>-a.png`），否则核验员只能判「无法判断」（v3 试跑中出现过）。核验员不评分，追加展开态不影响评论员的默认态基准。得到每条差距「已解决 / 部分解决 / 未解决 / 无法判断」与新问题。**差距解决率 = 已解决 ÷（总数 − 无法判断）**，部分解决单独列出。
2. **成对比较**：一次性执行即 Step 7 的「初始 vs 最终」结果；逐阶段执行为各阶段结果的汇总（每个维度在各阶段的判定链）。
3. **收尾绝对评分（评论员正文 A，1 次）**：对最终版本截图做一次绝对评分，作为本轮终点的参考值。它与初评双样本平均分比较时只作参考，单样本 ±1 的维度变化不单独定性。

**务实目标（达成判定）**——同时满足下列四条即「达成本轮目标」：
- 核验员判定：初评所有 P0、P1 差距为「已解决」（诊断报告中已归入「可改善上限」②依赖数据核对、③需功能或语义授权的差距除外，单独列出）；
- 成对比较：没有维度被判为「真退步」；
- 收尾绝对样本：没有 P0、P1 差距，且每个维度 ≥3；
- 保真核验：没有未授权的功能遗漏或语义漂移。

**顶尖参考线**：收尾绝对样本 ≥22/24（换算 ≥9.2）只作远景参考，单样本不足以证明，报告中写「接近 / 未接近参考线」，不作为成败结论。

按 [report-template.md](report-template.md)「收尾报告」输出：务实目标逐条结果、差距核验表、成对比较结果、评分轨迹（初评双样本平均 → 收尾单样本，仅参考）、硬性检查前后对比、保护清单、保真核验、剩余差距与可改善上限。

未达成时如实说明原因与剩余差距，可建议用户**另起一轮新诊断**（从 Step 2 重新开始，需用户主动发起）。不得在本次流程内自行追加轮次。

结束时告知 `./.ued-judge/` 下有截图、目标稿与备份，询问是否删除；用户不回应则保留。

## 3. 成本边界（硬上限）

| 用户选择 | 评论员调用 | 核验员调用 | 合计子智能体调用 |
|---|---|---|---|
| 只要报告 | 2（初评双样本） | 0 | 2 |
| 一次性执行 | 4（初评 2 + 收尾成对 1 + 收尾绝对 1） | 1 | 5 |
| 逐阶段执行 | ≤ 6（初评 2 + 每阶段成对 1，最多 3 + 收尾绝对 1） | 1 | ≤ 7 |

主控自检不计入。动态调整只能改写既有阶段的内容，**不能新增阶段、不能在同一流程内重新诊断**。任何超出上限的继续优化都必须是用户主动发起的新流程。

## 4. 隔离规则（评分客观性的底线）

1. 评论员与核验员每次都是全新上下文。
2. 评论员只拿到截图 + 使用途径。成对比较时拿到两套截图，**随机分配为 A/B，不告知新旧**；不给评语、代码、改动说明。
3. 每次使用逐字相同的冻结正文（正文 A / 正文 B / 核验员正文）。
4. 使用途径（含界面类型）首轮写定后不改。
5. 截图用同一脚本、同一参数，文件名中性。
6. **务实目标与顶尖参考线只存在于本协议与主控判断中**，不出现在任何传给评论员或核验员的内容里。
7. 主控不得「修正」评论员的判定或做解读性加减分。合并、平均与维度判定只影响**决策**，每个样本的原始输出照实记录。
8. 硬性检查结果、主控自检结论、改动清单都不传给评论员或核验员；核验员输出不传给评论员。
9. 本流程内评论员与核验员使用同一模型（见 Step 3）；模型变化须在报告中注明。
