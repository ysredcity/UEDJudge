# 默认控件边框保留与局部亮边修订

日期：2026-10-08。用户已确认分析方案，允许修改规则；不修改 TC1 页面、不重新运行评委、不提交或推送、不覆盖版本包。

## 原因与选择

「效果验证」对话（01a11965-c7f2-78a0-b4a9-abdd21c9f24c）中，普通版 1.4.0 原始 TC1 实跑把 H2 / visual-optimization 的「局部边界」建议落实为所有输入框、下拉框统一亮底边。用户认为没有必要；执行者也指出没有充分证明必要性，就由低对比数值推导出要增强边界。本轮不重写该次评委判定或核验记录，只记录规则决策的局限。

采用「默认保留轮廓，先判必要性，合规与视觉分别核验」。不继续推荐局部亮边替代整圈亮框，也不把 3:1 换成另一个统一的默认边框数值。后一做法仍会诱导逐项凑数值，并可能把真正不合规的必要线索当作已通过。

## 修改范围

- H2：默认组件边框无独立下限；需说明实际线索及必要性才能确定适用范围，不因低对比数值自动判断识别不足。必要线索与状态门槛保留，确认不足仍不通过，不清楚则无法判定。
- visual-optimization 与 X12：保留原有低权重、统一轮廓，不为补数值新增底边、单侧或局部亮线；原有下划线输入与必要状态指示不因此禁止，无描边控件也不被强制补框。
- 合规检查结果、视觉噪音和样式一致性分开记录，不能用边框比值提高证明优化有效，也不能用视觉协调宣称 AA 合规。
- Pro 共享副本只由 sync-pro-core 生成；SKILL 现有视觉参考索引仍适用，不重复添加正文。
- 新行为记入 Unreleased；现有 1.4.0 / Pro 1.0.0 ZIP 是修订前快照，原样保留，后续发布另行处理版本及打包。

## 人工边界复核

以下是规则一致性复核场景，不是模型行为测试或浏览器实测：

| 场景 | 应保持的决策 |
|---|---|
| 按钮可由合格的可操作文字识别，默认弱边框 | 不单独要求边框 3:1，不新增亮底边 |
| 只测到输入填充与边框对比较低，尚未说明必要线索 | 不凭两个数值自动判识别失败，也不自动通过；补足用途依据，不确定则无法判定 |
| 确认空输入的边界是唯一识别线索且未达 3:1 | H2 仍不通过；修复保持样式一致，不以新增一侧亮线凑数值 |
| 原设计体系已使用下划线输入框 | 不因局部线条样式判错，核验其实际必要线索 |
| 默认弱描边合适，但焦点、选中或勾选难以识别 | 状态要求不豁免；默认边框无独立门槛不等于状态通过 |
| 原有无框控件能被有效识别 | 不强制补完整轮廓，也不强制加底边 |
| 用户指定高对比主题 | 保留用户主题，不以降噪为由统一调暗 |

## 验证范围

执行两套 skill 结构校验、12 个共享文件一致性、6 项 Pro 报告测试、本地链接与 diff 检查；记录冻结正文/流程/模板、既有页面、全部 ZIP 及原有未提交文件的修改前后哈希。静态检查不能证明新规则不再被模型机械执行，真实效果待用户另起测试。

标准边界依据：[W3C Understanding SC 1.4.11 · Boundaries](https://www.w3.org/WAI/WCAG22/Understanding/non-text-contrast.html#boundaries)。无需独立检查边框不等于必要线索可以低于门槛，也不等于整页 AA 通过。

验证结果：两套 quick_validate、12 文件同步、6/6 Pro 测试、26 份 skill Markdown 中的 85 个本地链接及 diff 检查通过。18 个受保护文件修改前后哈希一致，涵盖冻结正文/协议/模板、入口、原始 TC1 与两份优化稿、四个历史/当前 ZIP 及原有其他未提交修改。以上 7 个边界场景已人工对照规则复核；没有另起模型实跑、浏览器优化或评委调用，不据此宣称行为收益。
